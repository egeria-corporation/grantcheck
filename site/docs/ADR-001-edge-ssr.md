# ADR-001: render entity pages at the edge, not as a static site

**Status:** accepted, 2026-09-01

## Context

There are roughly 1.4 million organizations described in section 501(c)(3), and this site's
whole purpose is a permanent, citable page for each one.

The obvious approach is a static site generator: build a page per organization, deploy, get
CDN performance for free. It does not work here, and it is the decision most likely to be
"optimised" later by somebody who has not read the numbers — which is why it is written
down.

## Decision

Render entity pages on demand at the edge from D1, and cache the result.

Pre-render at build time **only**: the landing page, `/methodology`, `/data`, the check
explainers, `/llms.txt` and `/robots.txt`.

## Why static does not work

**Cloudflare Pages allows 20,000 files per deployment on the free plan and 100,000 on paid.**
One page per organization exceeds the paid ceiling by more than an order of magnitude. Even
a meaningful fraction of it blows the 20-minute build timeout and destroys the deploy loop —
a one-character CSS change would mean a 20-minute build.

There is no performance argument on the other side. A cached edge render is served from the
same colo as a static asset. A cold render is one indexed D1 lookup against a table with a
primary key on the EIN.

## Consequences

- **Cache invalidation is keyed on the dataset vintage** rather than on TTL guesswork. Every
  cache key carries the concatenated dataset publication dates, so a new monthly ingest
  invalidates the entire edge cache in one step, with no purge call and no window in which
  two pages disagree about what the data says.
- **Every fact must be in the initial HTML.** No client-side fetching for anything primary.
  That is not a performance preference: a crawler or a language model that runs no
  JavaScript has to see the complete answer, and that is the entire reason the hosted layer
  exists. Adding a client-side fetch for primary content would silently void it, and would
  look like a performance improvement while doing so.
- **The check logic is reimplemented in TypeScript**, because the edge cannot run the Python
  library. Two implementations of one rule set is two sets of bugs, so `test/parity.test.ts`
  asserts the site's JSON against a fixture generated by the real Python tool. It is not
  optional: when it was first written it found seven differences, every one a place where a
  reader comparing the site to the command-line tool would have got a different answer.

## Alternatives considered

**Pre-render the top N organizations, edge-render the tail.** Adds a second code path and a
second cache story to maintain, for a first-byte saving that is already in the noise once
the edge cache is warm. Rejected as complexity without a benefit.

**Query the index shards from the Worker instead of D1.** The shards are compressed SQLite
built for a filesystem client; D1 is the same data in a form the edge can index and query
directly. Both come from the same ingest, so they cannot disagree about the underlying data.
